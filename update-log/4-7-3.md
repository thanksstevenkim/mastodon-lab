## Overview

Mastodon was upgraded from `v4.7.2` to `v4.7.3`.

This was a patch-level upgrade with no new database migrations, but it required
a production image rebuild because the release included application, frontend,
dependency, and asset changes.

The upstream tag was merged into a dedicated `update/4.7.3` branch before
being reviewed through GitHub Actions and merged into the fork's `main`
branch.

The production deployment was completed only after CI passed on the upgrade
branch and again after the merge to `main`.

## Upstream release highlights

Mastodon 4.7.3 included dependency updates and a collection of bug fixes.

Relevant changes included:

- account-data-removal logging
- a homepage link on the 404 error page
- stricter self-deletion confirmation behavior
- malformed WebFinger error handling
- an `aws-sdk-s3` update addressing a thread leak
- Yarn update to 4.18.1
- registration error handling for invalid date-of-birth input
- a fix preventing `POST /api/v1/accounts` from remaining available when
  `SSO_ACCOUNT_SIGN_UP` is configured
- account-deletion cleanup fixes
- normalized email handling for several Rack::Attack rate limits
- frontend and translation updates

The release notes also explicitly required asset recompilation.

## Registration controller compatibility

The 4.7.3 upstream update modified:

```text
app/controllers/auth/registrations_controller.rb
spec/controllers/auth/registrations_controller_spec.rb
```

These files are also customized in the Mustard fork for pre-registration
hCaptcha.

Although Git merged the files without a textual conflict, the combined behavior
was manually checked before deployment.

The resulting controller retained the local CAPTCHA integration:

```text
include Auth::CaptchaConcern
before_action :extend_csp_for_captcha!, only: [:new, :create]
check_captcha!
```

while also retaining the new upstream 4.7.3 invalid date-of-birth handling:

```text
rescue ActiveRecord::MultiparameterAssignmentErrors
handle_multiparameter_assignment_error
```

The confirmation controller also retained the local behavior that prevents a
web-created user from being challenged a second time during email confirmation.


## Sidekiq log review

A post-deployment log filter showed repeated
`ActivityPub::DeliveryWorker` failures for delivery to one remote Fediverse
server.

The errors included:

```text
Stoplight::Error::RedLight
```

and at least one remote HTTP 500 response.

These jobs were remote federation delivery retries rather than failures of the
local 4.7.3 application processes. The local web, Sidekiq, and streaming
containers remained healthy.

The remote-delivery condition was therefore treated as a separate federation
issue rather than an upgrade regression.

## Result

Upgrade completed successfully.

The main fork-specific risk in this update was the overlap between upstream
changes to `Auth::RegistrationsController` and the existing
pre-registration hCaptcha customization.

The absence of a Git conflict was not treated as sufficient validation.
The combined controller behavior was checked explicitly before CI and
production deployment.

No upgrade-related database migration or service failure was observed.

## Lessons learned

### Review semantic overlap even when Git reports no conflict

A clean merge does not guarantee that two changes affecting the same control
flow remain semantically compatible.

For maintained forks, files touched both upstream and locally should be
reviewed even when Git's merge strategy resolves them automatically.

### Preserve security customizations through upstream updates

The pre-registration CAPTCHA code is part of the current production abuse
mitigation rather than incidental fork drift.

Future Mastodon upgrades that modify registration controllers, confirmation
controllers, signup views, or CAPTCHA handling should explicitly verify that
the pre-registration barrier still runs before user persistence.

### Separate local failures from federation delivery failures

A healthy local deployment can still produce noisy Sidekiq exceptions when a
remote Fediverse server is unavailable or returns errors.

Post-deployment log review should distinguish remote delivery failures from
application startup, database, Redis, or local request-processing failures.

## Follow-up

- Continue monitoring normal web and federation behavior after deployment
- Keep pre-registration hCaptcha enabled
- Keep direct API signup restrictions under review as part of the layered
  registration-abuse mitigation
- Investigate repeated remote delivery failures separately if they persist
- Remove the `update/4.7.3` branch after the deployment has remained stable
