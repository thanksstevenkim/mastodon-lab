# Mastodon 4.7.2 Upgrade

## Overview

Mastodon was upgraded from `v4.7.1` to `v4.7.2`.

This was a relatively small patch release focused on bug fixes and security-related changes. No new database migrations were included.

During validation and deployment preparation, several issues specific to the fork and the upstream `v4.7.2` release process were identified and resolved:

- HEIF/AVIF-related RSpec failures caused by a mismatch between the `v4.7.2` release tag and upstream `main`
- OAuth application-related behavior adjusted in the fork
- A dark-theme regression that had existed since the `4.7.1` upgrade
- Server reboot performed after a kernel update

The service was verified as operational after the work was completed.

## Security change: HEIF support temporarily disabled

Mastodon 4.7.2 temporarily disables HEIF support.

The upstream change removed `VipsForeignLoadHeif` from the allowed libvips operations in:

```text
config/initializers/vips.rb
```

This affected both HEIC and AVIF processing through libvips.

The security change itself was kept unchanged.

## CI failure: HEIC and AVIF media specs

The first full RSpec run failed with two media attachment tests:

```text
MediaAttachment avif behaves like static 600x400 image
MediaAttachment heic behaves like static 600x400 image
```

The errors were:

```text
VipsForeignLoad: "...avif" is not a known file format
VipsForeignLoad: "...heic" is not a known file format
```

The full result was:

```text
7673 examples, 2 failures, 2 pending
```

The two existing pending tests were the expected MLDSA Object Integrity Proof specs.

### Investigation

The GitHub Actions environment was checked.

Relevant environment details:

```text
Ubuntu 24.04.5 LTS
libvips 8.15.1
libheif 1.17.6
```

The HEIF decoder packages were installed:

```text
libheif-plugin-aomdec
libheif-plugin-libde265
```

Ruby-level libvips inspection confirmed that the HEIF loaders were available:

```text
heifload: true
heifload_buffer: true
jpegload: true
pngload: true
webpload: true
```

This confirmed that the failure was not caused by missing system libraries.

### Root cause

The `v4.7.2` release tag disabled HEIF loading in `config/initializers/vips.rb`, but the release tag still contained media specs expecting AVIF and HEIC processing to succeed.

Upstream `main` had already adjusted the tests to skip those cases:

```ruby
describe 'avif', skip: 'HEIF temporarily disabled' do
```

```ruby
describe 'heic', skip: 'HEIF temporarily disabled' do
```

Upstream CI therefore reported:

```text
0 failures, 4 pending
```

while the `v4.7.2` tag itself still caused the two failures when tested directly.

### Resolution

The upstream test-only change was backported to the fork.

Only the following file was modified:

```text
spec/models/media_attachment_spec.rb
```

The HEIF security change itself was not reverted.

After the backport, CI completed successfully with the AVIF and HEIC specs marked as pending.

## Dark theme regression

A theme regression was identified after the 4.7.1 upgrade.

### Symptom

Selecting the Dark theme still resulted in the Light theme being displayed.

The issue had been present since 4.7.1.

### Root cause

The fork still contained an older customization in:

```text
app/views/layouts/application.html.haml
```

The fork used:

```haml
%html{ lang: I18n.locale }
```

Upstream 4.7 uses:

```haml
%html{ html_attributes }
```

In Mastodon 4.7, `html_attributes` includes not only the language attribute but also theme-related attributes such as:

```ruby
'data-contrast': contrast.parameterize,
'data-color-scheme': page_color_scheme.parameterize,
```

The old fork customization therefore prevented the expected `data-color-scheme` value from being added to the `<html>` element.

As a result, the theme selection script could not detect the configured dark color scheme correctly and fell back to the light theme.

### Resolution

The fork was restored to the upstream form:

```haml
%html{ html_attributes }
```

The locale behavior was preserved because `html_attributes` already includes:

```ruby
lang: I18n.locale
```

This was treated as fork drift rather than an intentional customization.

## Notes

This upgrade highlighted two different maintenance risks.

First, an upstream release tag can occasionally differ from the state used by upstream CI shortly afterward. In this case, the `v4.7.2` tag disabled HEIF support but did not yet contain the corresponding media-spec skips present in upstream `main`.

Second, old fork customizations can become incompatible with later upstream architecture changes even if they previously appeared harmless. The retained `%html{ lang: I18n.locale }` customization prevented Mastodon 4.7 theme attributes from being rendered and caused the dark-theme regression.

For future upgrades, customizations in shared layout and initialization files should be re-evaluated against upstream rather than automatically preserved.
